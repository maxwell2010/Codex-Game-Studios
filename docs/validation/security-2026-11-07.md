# Security review - 2026-11-07

## Scope and result

Reviewed the Codex adapter, CI, local lifecycle/download tooling, game fixture,
and shared shell helpers/hooks for dangerous execution and network patterns.
No confirmed secret exposure or critical exploit was identified within this
review. This is a bounded source/tooling review, not a penetration test or a
guarantee that every inherited workflow is safe on arbitrary untrusted input.

## Fixes and hardening

| Finding | Change |
| --- | --- |
| Generator could follow linked output directories/files outside its intended tree | Reject repository escapes, symlinks and Windows junctions on source and output paths; regression tests verify no overwrite |
| CI Actions used movable tags and retained checkout credentials | Pin official Action commit SHAs, disable credential persistence; retain contents: read and add a job timeout |
| Python dependency range allowed unreproducible resolution | Pin PyYAML 6.0.3; use safe_load, not arbitrary-object YAML loading |
| Future engine downloads could introduce unverified binaries | Fixed official release URLs, fixed SHA256 for Windows/Linux, size limit and extraction path checks; no global installation |
| Security policy sent reports to upstream and promised upstream response times | Fork-specific private reporting enabled and verified; fork policy added without unsupported SLA promises |
| Inherited prose could confuse runtime permissions | Explicitly retain Codex sandbox/approval boundaries and treat external content as data; hooks remain inactive in Codex |

These measures follow [GitHub's secure use guidance](https://docs.github.com/en/actions/reference/security/secure-use).

## Tool results

- `pip-audit 2.10.1 -r tools/requirements.txt`: PyYAML 6.0.3, **0 known vulnerabilities** at review time.
- `Bandit 1.9.4 -r tools`: original adapter had no findings. New replay/download
  tooling produces three findings, all reviewed: B310 on urlopen (fixed HTTPS
  URL from a constant allowlist, payload hash verified); B404 on subprocess import;
  B603 on subprocess.run (argument lists, no shell=True, user-selected local
  engine/Bash executables and fixed helper names). No suppression added.
- `detect-secrets 1.5.0`, whole working source tree with .git/.scratch/.godot
  excluded, verification disabled to avoid credential-validation network calls:
  **3 findings**, all non-secret documentation examples. Two are the literal
  BEGIN PRIVATE KEY search pattern in the source/adapted security skill; one is
  the intentionally incomplete sk_live_... token in a test scenario.
- Ten adapter regressions pass locally, including linked target protection,
  outside-root refusal and conversion without executing injected commands.
- Engine source package is built from five allowlisted files; it contains no
  repository config, credential files, studio hooks, logs or engine binaries.

Only the public Godot release host and package/advisory services were used by
validation tooling. The game itself has no networking, account system, native
extensions, shell execution, persistence or telemetry. Dependencies of the
temporary audit tools are not runtime dependencies of this repository.

## Remaining trust boundaries

- A checked-out skill or shell helper is executable developer material. Review
  changes before trusting a repository; a malicious instruction cannot be made
  safe by another instruction. No sandbox bypass is installed by this fork.
- Preserved upstream shell write helpers intentionally follow existing file
  links and are **not a filesystem sandbox**. Run them only in reviewed working
  copies with ordinary local files, as the isolated cycle does. The new Python
  generator's link protection does not apply to arbitrary shell commands.
- Upstream Claude session hooks can check GitHub for upstream releases and use
  a per-user cache; Codex does not enable or run those hooks. This review did not
  validate the Claude runtime.
- Custom engines, custom Bash binaries, OS toolchains and a modified fixture
  run with the invoking account's permissions. Do not point the runner at an
  untrusted executable. Hash verification protects the pinned downloaded payload,
  not a compromised developer machine or upstream GitHub account.
- No full-history secret audit, OS hardening assessment, multiplayer review,
  Unity/Unreal engine audit or adversarial prompt-injection benchmark was performed.
